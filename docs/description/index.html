This document describes the solution end to end: purpose, architecture, scenario map, sequence diagrams for each scenario, the conceptual class model, and the pilot case that confirmed the full cycle. All diagrams are embedded in the text; the PlantUML source is linked next to each one.

1. Purpose and scope

A local harness is needed for designing solution and software architecture and then implementing it. The process is performed by different roles within individual tasks and a shared plan: tasks have dependencies, statuses, an owning role, and acceptance criteria. Each role is a separate sub-agent running on a local Ollama model; external APIs are not used.

The solution covers:

  • harness: roles, board, task cards, process rules, commands, artifacts;
  • local models and tools: Ollama, local-rag, MCP plantuml-render, Git;
  • the pilot "Mini-CRUD service" as an end-to-end example: requirements -> ADR -> diagrams -> QA acceptance.

Out of scope: authentication, external integrations, production deployment, multi-user operation, pagination, and note search.

Key principles

  1. Single board - docs/plan.md is the only source of truth for the work scope.
  2. Single process - harness/process.md defines the lifecycle, statuses, artifact update order, and git discipline.
  3. Role isolation - each role writes only to its area and stays within task boundaries; nested subagent calls are forbidden.
  4. Deterministic acceptance - a task closes only by the card's acceptance criteria; failure is recorded in Blockers.
  5. Locality - models, embeddings, diagram rendering, and tests run locally.
  6. Traceability - decisions, diagrams, contracts, reviews, and commits are linked through task IDs.

2.3 Permissions and write areas

Role Write area Forbidden
harness lead writes no files; reads and delegates only edit/write, git commit, calling roles outside harness
orchestrator docs/**, README.md, .gitignore other roles' work, git push/tag/reset/rebase
analyst docs/analysis/**, docs/tasks/** (own status/log) architecture, code, tests, commits
architect docs/architecture/**, docs/tasks/** code, tests, editing docs/analysis
coder src/**, tests/**, scripts/**, Dockerfile, docker-compose*.yml, Makefile, .gitignore prod actions, git commit, docker push, cloud CLIs
qa docs/qa/**, docs/tasks/** fixing code/artifacts, commits, deployment
doc-writer README.md, docs/guides/**, docs/architecture/adr-*.md (editing) code, tests, CI/CD, changing ADR meaning

Permissions include both relative and **/... pattern variants: opencode matches edit/write against the absolute path, so the blanket deny "*": "deny" is overridden by a specific allow matching the full path. .gitignore is allowed for orchestrator and coder. All roles may create issue files in docs/issues/**; the orchestrator maintains the index.

Common prohibitions: editing ~/.config/opencode/**, secrets in code/logs/commits, nested subagent calls, access outside drive C:, production deployment.

4. Scenarios

S-01. Harness installation and bootstrap

Goal: install harness globally once and initialize it in the project. Preconditions: the harness source repository is available, Ollama is running, models are loaded.

Source: diagrams/seq-01-bootstrap.puml.

Result: agents, commands, skill, templates, and scripts are in ~/.config/opencode/; the project has harness/process.md, harness/version.json, and docs/plan.md. Note: default_agent is not changed; an opencode restart is required after installing agents. Activation is only via explicit /harness-*.

S-02. Full task cycle (/harness-run)

Goal: take a task from dependency checks through acceptance and commit. Preconditions: the project is initialized (harness/process.md), the card docs/tasks/T-XXX-*.md exists, all depends_on are done, and no other task is in_progress. Tasks run strictly sequentially - parallel starts are forbidden.

Source: diagrams/seq-02-harness-run.puml.

Result: the task is done, the board, card, activity diagram, and SVG are updated, and a commit T-XXX: ... is made; dependent tasks are unblocked. Errors: no marker - stop and suggest /harness-init; unmet dependencies - stop without starting; another task in_progress - stop without changing statuses; acceptance failure - failed and cause in Blockers.

S-03. Requirements analysis (analyst)

Goal: collect and refine requirements and check existing materials via RAG. Preconditions: a statement exists and local-rag is available (when Ollama is unavailable, RAG works in FTS5 mode).

Source: diagrams/seq-03-analyst.puml.

Result: docs/analysis/requirements-*.md with atomic verifiable requirements R-NNN, questions-*.md with open questions and assumptions, glossary.md; an orchestrator report with risks and blockers. Errors: missing data is recorded as a question, not as an invented requirement.

S-04. Architecture and diagrams (architect)

Goal: make an architectural decision with alternatives, produce diagrams and contracts. Preconditions: analyst requirements are accepted.

Source: diagrams/seq-04-architect.puml.

Result: an ADR from the template, component/sequence diagrams .puml + .svg, interface contracts, and decomposition for the coder. Mandatory control: every diagram passes check_syntax, then render_file; syntax errors are fixed before handoff. A decision without alternatives is not acceptable.

S-05. Implementation and tests (coder)

Goal: implement strictly per ADRs and contracts. Preconditions: ADRs and contracts are accepted; the task includes a local run target.

Source: diagrams/seq-05-coder.puml.

Result: code in src/, tests in tests/, CI/CD preparation (Dockerfile, compose, Makefile, scripts), green tests, and a locally running service. Errors: failing tests are fixed without weakening assertions; when context is insufficient - stop with a blocker, not a partial implementation.

S-06. QA acceptance (qa)

Goal: independently verify artifacts against acceptance. Preconditions: the role results were passed by the orchestrator.

Source: diagrams/seq-06-qa.puml.

Result: docs/qa/review-T-XXX.md with a "criterion -> pass/fail" table, findings by severity, and an accept/reject verdict; an independent test run (read-only) and visual diagram review. Errors: reject returns the task for fixes; QA does not edit artifacts itself.

S-07. Documentation (doc-writer)

Goal: bring documentation in line with the actual solution. Preconditions: ADRs, contracts, and implementation are available.

Source: diagrams/seq-07-doc-writer.puml.

Result: README, runbook, guides, ADR finalization from the template; relative links, verified commands. Constraint: do not change the meaning of ADRs and contracts - only form and completeness.

S-08. Board sync (harness-board-update)

Goal: bring the plan, cards, and activity diagram in line with the actual state. Preconditions: the project is initialized; tasks are completed or statuses changed.

Source: diagrams/seq-08-harness-board-update.puml.

Result: the harness lead delegates to harness-orchestrator: update docs/plan.md, cards, docs/activity.puml colors, re-render docs/activity.svg, record commit hashes, and commit chore: board update (...). Rule: on divergence, the task card is the source of truth.

S-09. Board report (harness-board-report)

Goal: get a summary without changing artifacts. Preconditions: the project is initialized.

Source: diagrams/seq-09-harness-board-report.puml.

Result: the harness lead delegates to harness-orchestrator for a read-only summary: status table, tasks ready to start, failed/blocked with causes, %done, dangling dependency check, 1-3 recommendations. Rule: the scenario is strictly read-only; nothing is committed.

S-10. Errors, retries, and blockers

Goal: handle acceptance failure predictably without losing history. Preconditions: the role returned a result; the orchestrator performed acceptance.

Source: diagrams/seq-10-errors.puml.

Result: on failure the task becomes failed, the cause and output are written to the card; up to 3 fix attempts are made; after exhaustion - blocked and escalation to the user. Error history is not deleted during fixes.

S-11. Pilot end-to-end cycle T-013

Goal: prove the full cycle works on a separate task. Preconditions: harness is assembled (T-001..T-012), roles are available.

Source: diagrams/seq-11-pilot-e2e.puml.

Result: the analyst produced pilot requirements, the architect - an ADR and component diagram, QA - a review with verdict accept; T-013 is done, a commit is made. The pilot confirmed that role prompts are sufficiently deterministic.

5. Conceptual class model

Source: diagrams/class-harness.puml.

The model is conceptual: it describes the harness domain (board, tasks, roles, artifacts), not the classes of a specific application.

Class Purpose
PlanBoard board docs/plan.md: load tasks, change status, record a commit
TaskCard task card: id, role, dependencies, acceptance, artifacts, blockers, log
TaskStatus statuses pending, in_progress, done, failed, blocked
Role abstract role: model, permissions, write areas, task execution
Orchestrator, Analyst, Architect, Coder, QA, DocWriter concrete harness roles
ModelProfile local model, thinking mode, purpose
Artifact role artifact with path, type, and producer
Diagram PlantUML source and SVG render; validation and rendering
Review QA report: verdict and findings list
Finding finding with ID, severity, and text
Commit task git commit: hash and message
Command opencode command: /harness-run, /harness-board-update, /harness-board-report
HarnessLead primary agent harness: marker, routing, report; writes no files
LogEntry task card log entry
RoleResult role result: status, files, summary

Key relationships: PlanBoard 1 *-- 0..* TaskCard; TaskCard depends on other cards (dependsOn), is assigned to one role, and has one status; a role produces many artifacts; Diagram and Review inherit Artifact; HarnessLead is selected by a command, reads the board/cards, and calls roles; the orchestrator updates the board and creates commits.

6. Process, statuses, and control

6.1 Task lifecycle

  1. The harness lead checks the project marker, depends_on (all done), and that no other task is in_progress.
  2. harness-orchestrator sets the task to in_progress (plan, card, diagram color).
  3. The role performs the task strictly per the card's acceptance.
  4. harness-orchestrator accepts the result; on failure - failed.
  5. Status -> done, log entry, board/activity/SVG update, and commit.

Tasks run strictly sequentially: at most one in_progress at a time; parallel task starts are forbidden.

6.2 Statuses

Status Color Meaning
pending #D3D3D3 not started
in_progress #FFE082 in progress
done #90EE90 completed and accepted
failed #FF9090 error, fix required
blocked #FFB347 external blocker

Allowed transitions: pending -> in_progress -> done; in_progress -> failed; failed -> in_progress (after a fix); * -> blocked on an external blocker.

6.3 Mandatory artifact update order

  1. docs/plan.md - status, artifacts, commit hash.
  2. docs/tasks/T-XXX-*.md - status, log, blockers.
  3. docs/activity.puml - task block color.
  4. Re-render docs/activity.svg via MCP plantuml-render.
  5. git commit with message T-XXX: ....

6.4 Git discipline

  • Repository at the project root; default branch master.
  • At least one commit per task; format T-XXX: short description.
  • Forbidden: git push, git tag, history rewrite, committing secrets and .env.
  • Only task files are included in the commit.

6.5 Plan execution diagram

Source: docs/activity.puml. Green - done, gray - pending, yellow - in_progress, red - failed, orange - blocked.

6.6 Issue log

Harness problems are recorded by the harness-issues skill:

  • docs/issues/ISSUE-YYYYMMDD-HHMMSS-<slug>.md - one problem;
  • docs/issues/README.md - index list.

A record contains status, severity, type, source, role, absolute location, symptoms, reproduction, cause, solution/workaround, verification, prevention, and timeline. All roles may create issue files; harness-orchestrator verifies the index and includes them in the task commit. Secrets are never written to issues.

7. Pilot case "Mini-CRUD service" (T-013)

The pilot checks the analyst -> architect -> qa cycle on a separate task: REST CRUD for notes, SQLite, local Docker, deterministic tests. One user, no auth, no external integrations.

7.1 Requirements

ID Requirement
R-001 POST /notes with title, body; response 201 with id.
R-002 GET /notes - array of notes, sorted by created_at descending.
R-003 GET /notes/{id}; 404 if missing.
R-004 PUT /notes/{id} with title, body; 404 if missing.
R-005 DELETE /notes/{id}; 204 on success, 404 if missing.
R-006 Validation: title 1..200 characters, body up to 10000; error 422.
NFR-1 docker compose up starts the service on port 8080.
NFR-2 SQLite file in a volume; survives container restart.
NFR-3 Unit + API tests, deterministic, no network.

Pilot open questions: pagination is not needed (Q-001), full-text search is out of scope (Q-002). Risks: SQLite file growth (R1), no auth - local/staging only (R2). Full requirements: docs/analysis/pilot-requirements.md.

7.2 Architectural decision (ADR-001)

Stack: Python 3.12 + FastAPI + SQLAlchemy 2.x (SQLite) + Pydantic v2. Structure: thin API layer -> service layer -> repository. Tests: pytest + httpx (ASGI transport). Container: python:3.12-slim, docker compose with a DB volume.

Alternative Why rejected
Flask + SQLite manual validation, less typing
Node/Express + better-sqlite3 second stack in the local environment
Django + DRF overkill for one CRUD

Full ADR: docs/architecture/pilot-adr.md.

7.3 REST contract

Method Path Body Response
POST /notes {title, body} 201 {id, title, body, created_at}
GET /notes - 200 [...]
GET /notes/{id} - 200 / 404
PUT /notes/{id} {title, body} 200 / 404
DELETE /notes/{id} - 204 / 404

Errors: {"detail": "..."}; validation - 422 (Pydantic).

8. Operations

8.1 Global installation and quick start

  1. From the repository root, run the global installation: powershell -NoProfile -ExecutionPolicy Bypass -File harness/scripts/install.ps1.
  2. Restart opencode; check the installation with /harness-doctor.
  3. In the project, run /harness-init; check harness/process.md and docs/plan.md.
  4. Fill in docs/plan.md and create a card from harness/templates/task-card.md.
  5. Start a task with /harness-run T-XXX.
  6. Summary: /harness-board-report; sync: /harness-board-update all.
  7. Diagram: docs/activity.puml, render: docs/activity.svg.

default_agent is not switched to harness: activation is only via explicit /harness-*. Global installation is per current user (~/.config/opencode).

8.2 Commands

Command Argument Purpose
/harness-init - create harness and marker files in the current project
/harness-run T-XXX dependency checks, in_progress, role call, acceptance, commit
/harness-board-update T-XXX or all reconcile statuses, commits, activity diagram, and SVG
/harness-board-report - read-only summary: statuses, blockers, ready tasks, recommendations
/harness-doctor - check the global installation and the current project

8.3 How to add a task

  1. Create a card from harness/templates/task-card.md.
  2. Add a row to docs/plan.md from harness/templates/plan-row.md.
  3. Specify the role, depends_on, acceptance, and artifacts.
  4. Run harness-run T-XXX after dependencies are done.
  5. After the task, update the board/card/diagram and commit.

8.4 Limitations and risks

  • SQLite is not designed for concurrent writes - accepted for the pilot.
  • No auth - the service is local/staging only.
  • Models are local: quality and speed depend on hardware; when Ollama is unavailable, RAG works in FTS5 mode.
  • Diagrams and documentation require periodic reconciliation with code.
  • Role prompts are deterministic but do not guarantee a perfect first pass - failed and retry <= 3 are provided.

8.5 HTML build

The HTML version is generated from this file and requires no network:

python docs/description/build_html.py

The script embeds all SVGs as data: URIs, wraps diagrams in zoomable figures, and builds docs/description/index.html. The page template and modal styles/JS are in docs/description/template.html. Python 3.12 and the markdown package are required.

8.6 Troubleshooting

Symptom Cause Action
role is not visible in opencode agents were added after startup restart opencode
model is unavailable Ollama is not running / model is not loaded start Ollama, ollama pull
RAG answers without embeddings Ollama is unavailable FTS5 mode; does not block the task
diagram does not render PlantUML error check_syntax, fix .puml, rerun render_file
task does not start a dependency is not done check depends_on and card statuses
