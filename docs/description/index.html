This document describes the solution end to end: purpose, architecture, scenario map, sequence diagrams for each scenario, the conceptual class model, and the pilot case that confirmed the full cycle. All diagrams are embedded in the text; the PlantUML source is linked next to each one.

1. Purpose and scope

A local harness is needed for designing solution and software architecture and then implementing it. The process is performed by different roles within individual tasks and a shared plan: tasks have dependencies, statuses, an owning role, and acceptance criteria. Each role is a separate sub-agent running on a local Ollama model; external APIs are not used.

The solution covers:

  • harness: roles, two workflows, board, task/bug cards, checkpoints, process rules, commands, artifacts;
  • local models and tools: Ollama, local-rag, MCP plantuml-render, Git;
  • feature flow: requirements -> UC-E2E-NNN -> YAML data -> automated tests -> QA coverage/verdict;
  • bugfix flow: BUG-XXX report -> reproduction + failing regression -> minimal fix -> independent QA fail-before/pass-after -> closure/postmortem;
  • UX flow: user flows -> screens -> wireframes -> UI spec -> HTML prototype;
  • the pilot "Mini-CRUD service" as an end-to-end example: requirements -> ADR -> diagrams -> QA acceptance.

Out of scope: authentication, external integrations, production deployment, multi-user operation, pagination, and note search.

Key principles

  1. Single board - docs/plan.md is the only execution queue for both workflows.
  2. Single shared process - harness/process.md defines shared rules; harness/workflows/feature.md and bugfix.md define stages and gates.
  3. One active task - feature and bugfix never run in parallel and cannot preempt each other.
  4. Role isolation - each role writes only to its area and stays within task boundaries; nested subagent calls are forbidden.
  5. Deterministic acceptance - a task closes only by the card's acceptance criteria and explicit CP-F approval; failure is recorded in Blockers.
  6. User control - every task stops at checkpoints; user edits and decisions are authoritative.
  7. Evidence first - feature e2e traceability and bugfix fail-before/pass-after evidence are mandatory gates, not optional notes.
  8. Separate registries - product defects in docs/bugs/, harness problems in docs/issues/.
  9. Locality - models, embeddings, diagram rendering, and tests run locally.
  10. Traceability - decisions, diagrams, contracts, reviews, and commits are linked through task and bug IDs.

4. Scenarios

S-01. Harness installation and bootstrap

Goal: install harness globally once and initialize it in the project. Preconditions: the harness source repository is available, Ollama is running, models are loaded.

Source: diagrams/seq-01-bootstrap.puml.

Result: agents, commands, skills, workflows, templates, and scripts are in ~/.config/opencode/; the project has harness/process.md, harness/workflows/, harness/version.json, docs/plan.md, docs/bugs/, docs/ux/, and docs/checkpoints/. Note: default_agent is not changed; an opencode restart is required after installing agents. Activation is only via explicit /harness-*.

S-02. Task cycle with checkpoints (/harness-run)

Goal: take a task from dependency checks through user checkpoints, acceptance, and commit. Preconditions: the project is initialized (harness/process.md), the card docs/tasks/T-XXX-*.md exists with a valid workflow/stage, its workflow file is present, all depends_on are done, and no other task is active (in_progress or awaiting_review). Tasks run strictly sequentially across both workflows - parallel starts and feature/bugfix preemption are forbidden.

Source: diagrams/seq-02-harness-run.puml.

Result: at each checkpoint the task is awaiting_review with a checkpoint file and snapshot commit; after the user's explicit approved decision and CP-F, the task is done, the board/card/activity/SVG are updated, and a commit T-XXX: ... is made; dependent tasks are unblocked. Errors: no marker - stop and suggest /harness-init; unmet dependencies - stop without starting; another active task - stop without changing statuses; no checkpoint decision - stop and ask, never infer approval; acceptance failure - failed and cause in Blockers.

S-03. Requirements and e2e use cases (analyst)

Goal: collect and refine requirements, check existing materials via RAG, and formalize end-to-end use cases with test data. Preconditions: a statement exists and local-rag is available (when Ollama is unavailable, RAG works in FTS5 mode).

Source: diagrams/seq-03-analyst.puml.

Result: docs/analysis/requirements-*.md with atomic verifiable requirements R-NNN, questions-*.md with open questions and assumptions, glossary.md, e2e-use-cases-*.md with UC-E2E-NNN and a coverage matrix, and e2e-test-data-*.yaml (schema harness-e2e/1); an orchestrator report with risks and blockers. Rules: every functional requirement is covered by a use case or explicitly out_of_scope; the dataset contains no secrets and every use case has expected results and cleanup. Errors: missing data is recorded as a question, not as an invented requirement or use case.

S-04. Architecture and diagrams (architect)

Goal: make an architectural decision with alternatives, produce diagrams and contracts. Preconditions: analyst requirements and e2e use cases are accepted; UX screen IDs/UI spec are available when the task has a UI.

Source: diagrams/seq-04-architect.puml.

Result: an ADR from the template, component/sequence diagrams .puml + .svg, interface contracts, and decomposition for the coder. Mandatory control: every diagram passes check_syntax, then render_file; syntax errors are fixed before handoff. A decision without alternatives is not acceptable.

S-05. Implementation, unit and e2e tests (coder)

Goal: implement strictly per ADRs, contracts, and UX specs, including deterministic e2e automation. Preconditions: ADRs, contracts, UX specs, and the analyst e2e dataset are accepted; the task includes a local run target.

Source: diagrams/seq-05-coder.puml.

Result: code in src/, unit/integration tests, tests/e2e/, a dataset validator (scripts/validate-e2e-data.py), an isolated e2e runner (scripts/e2e.ps1 or make e2e) with seed/cleanup and per-UC-E2E results, CI/CD preparation (Dockerfile, compose, Makefile), green tests, and a locally running service. Errors: failing tests are fixed without weakening assertions; e2e uses only local/staging resources; when context is insufficient - stop with a blocker, not a partial implementation.

S-06. QA acceptance and e2e coverage (qa + qa-vision)

Goal: independently verify artifacts against acceptance, including e2e coverage and execution. Preconditions: the role results were passed by the orchestrator; the coder provided an e2e runner and dataset validator.

Source: diagrams/seq-06-qa.puml.

Result: docs/qa/e2e-plan-*.md with a requirement -> UC-E2E-NNN -> test matrix, docs/qa/e2e-report-*.md with run evidence, defects, and residual risks, and docs/qa/review-T-XXX.md with a "criterion -> pass/fail" table, findings by severity, and an accept/reject verdict; an independent unit/integration/e2e run (read-only). For visuals, the lead then runs a separate qa-vision pass and the orchestrator combines both reports into one verdict. Errors: reject returns the task for fixes; QA does not edit code, tests, or artifacts itself; e2e never touches production.

S-07. Documentation (doc-writer)

Goal: bring documentation in line with the actual solution. Preconditions: ADRs, contracts, and implementation are available.

Source: diagrams/seq-07-doc-writer.puml.

Result: README, runbook, guides, ADR finalization from the template; relative links, verified commands. Constraint: do not change the meaning of ADRs and contracts - only form and completeness.

S-08. Board sync (harness-board-update)

Goal: bring the plan, cards, and activity diagram in line with the actual state. Preconditions: the project is initialized; tasks are completed or statuses changed.

Source: diagrams/seq-08-harness-board-update.puml.

Result: the harness lead delegates to harness-orchestrator: update docs/plan.md, cards, the bug index/links, docs/activity.puml colors, re-render docs/activity.svg, record commit hashes, and commit chore: board update (...). Rule: on divergence, the task card is the source of truth; board update is forbidden while a task is active.

S-09. Board report (harness-board-report)

Goal: get a summary without changing artifacts. Preconditions: the project is initialized.

Source: diagrams/seq-09-harness-board-report.puml.

Result: the harness lead delegates to harness-orchestrator for a read-only summary: tasks by workflow, bug queue and severity, tasks ready to start, failed/blocked with causes, %done, dangling dependency and bug/task mismatch checks, 1-3 recommendations. Rule: the scenario is strictly read-only; nothing is committed.

S-10. Errors, retries, and blockers

Goal: handle acceptance failure predictably without losing history. Preconditions: the role returned a result; the orchestrator performed acceptance.

Source: diagrams/seq-10-errors.puml.

Result: on failure the task becomes failed, the cause and output are written to the card; up to 3 fix attempts are made; after exhaustion - blocked and escalation to the user. Error history is not deleted during fixes.

S-11. Pilot end-to-end cycle T-013

Goal: prove the full cycle works on a separate task. Preconditions: harness is assembled (T-001..T-012), roles are available.

Source: diagrams/seq-11-pilot-e2e.puml.

Result: the analyst produced pilot requirements, the architect - an ADR and component diagram, QA - a review with verdict accept; T-013 is done, a commit is made. The pilot confirmed that role prompts are sufficiently deterministic.

S-12. UX design (ux-designer)

Goal: turn accepted requirements and e2e use cases into reviewable UX artifacts. Preconditions: requirements and UC-E2E are accepted; the card marks ux: required.

Source: diagrams/seq-12-ux-designer.puml.

Result: docs/ux/user-flows-*.md, screens-*.md, wireframes-*.puml + .svg, ui-spec-*.md, and a static HTML prototype. Screen IDs are stable and referenced by architecture contracts and e2e use cases. The role stops at its checkpoint; QA vision and the user review the visuals. Errors: missing requirements - stop and ask the analyst; no production code, external CDNs, or real user data.

S-13. User checkpoints

Goal: give the user a reliable review/edit/approve point without losing task context. Preconditions: the role reached a declared checkpoint.

Source: diagrams/seq-13-checkpoints.puml.

Result: the task is awaiting_review; docs/checkpoints/T-XXX-CP-N.md records artifacts, snapshot commit, user remarks/edits, and the decision. On approved the role continues; on changes_requested it returns to the same checkpoint. CP-F is mandatory before done. Errors: missing decision - stop and ask; user edits - authoritative, preserve them; at most one task may be awaiting_review.

S-14. Bugfix workflow (/harness-bug -> /harness-run)

Goal: restore expected behavior through a durable BUG-XXX report, a reproduction, a failing regression test, a minimal fix, and independent QA. Preconditions: the expected behavior exists; a report has observed/expected behavior, reproduction, and environment; no other active task.

Source: diagrams/seq-14-bugfix.puml.

Result: docs/bugs/BUG-XXX-*.md and the index are updated; the coder stops at CP-1 with reproduction/root cause and a regression test that fails on the base revision, then at CP-2 with the minimal fix and green regression. QA verifies fail-before/pass-after independently and records docs/qa/review-T-XXX.md. The bug moves fixed -> verified -> closed only after CP-F; P0/P1 require a postmortem. Errors: missing reproduction data - keep the bug new and ask; no speculative fix. Contract/schema/security/multi-module/UI-flow changes escalate to feature-style analysis and design.

6. Process, statuses, and control

6.1 Task lifecycle

  1. The harness lead reads the card's workflow/stage, loads the matching workflow file, checks the project marker, depends_on (all done), and that no other task is active (in_progress or awaiting_review).
  2. harness-orchestrator sets the task to in_progress (plan, card, diagram color) and updates the linked bug to in_progress for the first bugfix task.
  3. The role performs the current stage strictly per the card's acceptance and stops at the next checkpoint; bugfix cannot pass reproduction without a failing regression test.
  4. The orchestrator creates docs/checkpoints/T-XXX-CP-N.md, sets awaiting_review, updates the bug status when applicable, and commits a snapshot.
  5. The user reviews/edits artifacts and records approved or changes_requested; /harness-run resumes the role.
  6. After the final role checkpoint and CP-F approval, harness-orchestrator accepts the result; on failure - failed.
  7. Status -> done, bug status (fixed/verified/closed), log entry, board/activity/SVG update, and commit.

Tasks run strictly sequentially across both workflows: at most one task is in_progress or awaiting_review at a time; feature/bugfix preemption and parallel task starts are forbidden. New pending cards and bug reports may be registered while a task is active.

6.2 Statuses

Status Color Meaning
pending #D3D3D3 not started
in_progress #FFE082 in progress
awaiting_review #87CEFA waiting for user checkpoint review
done #90EE90 completed, accepted, CP-F approved
failed #FF9090 error, fix required
blocked #FFB347 external blocker

Allowed transitions: pending -> in_progress; in_progress -> awaiting_review at a checkpoint; awaiting_review -> in_progress after approval or a change request, except CP-F approval which goes to done; awaiting_review -> done only after CP-F approval; in_progress -> failed; failed -> in_progress (after a fix); * -> blocked on an external blocker.

6.3 Mandatory artifact update order

  1. docs/plan.md - workflow, status, artifacts, bug link, commit hash.
  2. docs/tasks/T-XXX-*.md - status, log, blockers, checkpoint list.
  3. docs/bugs/BUG-XXX-*.md and docs/bugs/README.md - bug status, tasks, root cause, fix, verification (orchestrator only).
  4. docs/activity.puml - task block color.
  5. Re-render docs/activity.svg via MCP plantuml-render.
  6. docs/checkpoints/T-XXX-CP-N.md - artifacts, decision, user remarks/edits, snapshot commit.
  7. git commit with checkpoint snapshot message or final T-XXX: ....

6.4 Git discipline

  • Repository at the project root; default branch master.
  • At least one commit per task; format T-XXX: short description.
  • Forbidden: git push, git tag, history rewrite, committing secrets and .env.
  • Only task files are included in the commit.

6.5 Plan execution diagram

Source: docs/activity.puml. Green - done, gray - pending, yellow - in_progress, blue - awaiting_review, red - failed, orange - blocked.

6.6 Bug and issue logs

Product defects use the BUG-XXX registry:

  • docs/bugs/BUG-XXX-<slug>.md - one bug report, root cause, fix, verification;
  • docs/bugs/README.md - bug index.

Harness problems are recorded by the harness-issues skill:

  • docs/issues/ISSUE-YYYYMMDD-HHMMSS-<slug>.md - one problem;
  • docs/issues/README.md - index list.

A harness issue record contains status, severity, type, source, role, absolute location, symptoms, reproduction, cause, solution/workaround, verification, prevention, and timeline. All roles may create issue files; the harness-orchestrator verifies the index and includes them in the task commit. Only docs/issues/ is valid; a root harness-issues/ directory is not a registry. /harness-doctor checks the index in both directions. Only the orchestrator edits bug cards. Secrets are never written to either log.

7. Pilot case "Mini-CRUD service" (T-013)

The pilot checks the analyst -> architect -> qa cycle on a separate task: REST CRUD for notes, SQLite, local Docker, deterministic tests. One user, no auth, no external integrations.

7.1 Requirements

ID Requirement
R-001 POST /notes with title, body; response 201 with id.
R-002 GET /notes - array of notes, sorted by created_at descending.
R-003 GET /notes/{id}; 404 if missing.
R-004 PUT /notes/{id} with title, body; 404 if missing.
R-005 DELETE /notes/{id}; 204 on success, 404 if missing.
R-006 Validation: title 1..200 characters, body up to 10000; error 422.
NFR-1 docker compose up starts the service on port 8080.
NFR-2 SQLite file in a volume; survives container restart.
NFR-3 Unit + API tests, deterministic, no network.

Pilot open questions: pagination is not needed (Q-001), full-text search is out of scope (Q-002). Risks: SQLite file growth (R1), no auth - local/staging only (R2). Full requirements: docs/analysis/pilot-requirements.md.

7.2 Architectural decision (ADR-001)

Stack: Python 3.12 + FastAPI + SQLAlchemy 2.x (SQLite) + Pydantic v2. Structure: thin API layer -> service layer -> repository. Tests: pytest + httpx (ASGI transport). Container: python:3.12-slim, docker compose with a DB volume.

Alternative Why rejected
Flask + SQLite manual validation, less typing
Node/Express + better-sqlite3 second stack in the local environment
Django + DRF overkill for one CRUD

Full ADR: docs/architecture/pilot-adr.md.

8. Operations

8.1 Global installation and quick start

  1. From the repository root, run the global installation: powershell -NoProfile -ExecutionPolicy Bypass -File harness/scripts/install.ps1.
  2. Restart opencode; check the installation with /harness-doctor.
  3. In the project, run /harness-init; check harness/process.md, harness/workflows/, and docs/plan.md.
  4. Start a feature with /harness-feature <slug> [e2e] [ux] or a bug with /harness-bug <report>; review the created pending cards.
  5. Start a task with /harness-run T-XXX; stop at the checkpoint, review/edit artifacts, record a decision, and resume.
  6. Summary: /harness-board-report; sync: /harness-board-update all.
  7. Diagram: docs/activity.puml, render: docs/activity.svg.

default_agent is not switched to harness: activation is only via explicit /harness-*. Global installation is per current user (~/.config/opencode).

8.2 Commands

Command Argument Purpose
/harness-init - create harness, workflows, bug registry, and marker files in the current project
/harness-feature <slug> [e2e] [ux] create a pending P-00 feature planning task
/harness-bug <report or BUG-XXX> create/triage a BUG-XXX card and pending bugfix tasks
/harness-run T-XXX workflow/dependency checks, in_progress, role call, checkpoint, resume, acceptance, commit
/harness-board-update T-XXX or all reconcile statuses, bug index, checkpoints, commits, activity diagram, and SVG when no task is active
/harness-board-report - read-only summary: tasks by workflow, bug queue, pending reviews, blockers, recommendations
/harness-doctor - check the global installation and the current project

8.3 How to add work

  1. Use /harness-feature <slug> [e2e] [ux] for new behavior or /harness-bug <report> for a defect.
  2. The orchestrator creates a card from harness/templates/task-card-feature.md or task-card-bugfix.md (bugfix also gets a docs/bugs/BUG-XXX-*.md card).
  3. Add/verify the row in docs/plan.md from harness/templates/plan-row.md.
  4. Specify workflow, stage, role, depends_on, acceptance, inputs, e2e/UX or bug/severity applicability, and checkpoints (at least CP-F).
  5. Run /harness-run T-XXX after dependencies are done; never start a second active task.
  6. Review each checkpoint, record a decision, and resume; after CP-F, update the board/card/bug/diagram and commit.

8.4 Limitations and risks

  • SQLite is not designed for concurrent writes - accepted for the pilot.
  • No auth - the service is local/staging only.
  • Models are local: quality and speed depend on hardware; when Ollama is unavailable, RAG works in FTS5 mode.
  • Diagrams and documentation require periodic reconciliation with code.
  • Role prompts are deterministic but do not guarantee a perfect first pass - failed and retry <= 3 are provided.
  • E2E tests target local/staging only; production data and deployment are forbidden.
  • Feature and bugfix work never run in parallel; a hotfix waits behind the active task instead of preempting it.
  • A bugfix without a reproducible failure stays blocked at CP-1; no speculative fix is allowed.
  • Checkpoints require explicit user decisions; stale checkpoint files are caught during board reconciliation, not automatically.

8.5 HTML build

The HTML version is generated from this file and requires no network:

python docs/description/build_html.py

The script embeds all SVGs as data: URIs, wraps diagrams in zoomable figures, and builds docs/description/index.html. The page template and modal styles/JS are in docs/description/template.html. Python 3.12 and the markdown package are required.

second task was requested one active task exists across both workflows finish or review the active task; no preemption

product bug was filed in docs/issues/ wrong registry move it to docs/bugs/; keep harness issues separate
