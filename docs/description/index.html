Документ описывает решение целиком: назначение, архитектуру, карту сценариев, sequence-диаграммы каждого сценария, концептуальную модель классов и пилотный кейс, подтвердивший полный цикл. Все схемы встроены в текст; рядом с каждой указан исходник PlantUML.

1. Назначение и область

Нужен локальный harness для проектирования архитектуры решений и ПО с последующей реализацией. Процесс выполняется разными ролями в рамках отдельных задач и общего плана: у задач есть зависимости, статусы, ответственная роль и критерии приёмки. Каждая роль — отдельный sub-agent, работающий на локальной модели Ollama; внешние API не используются.

В область решения входят:

  • harness: роли, board, карточки задач, регламент, команды, артефакты;
  • локальные модели и инструменты: Ollama, local-rag, MCP plantuml-render, Git;
  • пилотный «Мини-CRUD сервис» как сквозной пример: требования → ADR → схемы → QA-приёмка.

Вне области: аутентификация, внешние интеграции, production-деплой, многопользовательская работа, пагинация и поиск по заметкам.

Ключевые принципы

  1. Единый board — docs/plan.md единственный источник истины по составу работ.
  2. Единый регламент — harness/process.md задаёт жизненный цикл, статусы, порядок обновления артефактов и git-дисциплину.
  3. Изоляция ролей — каждая роль пишет только в свою зону и не выходит за границы задачи; вложенные вызовы sub-agent'ов запрещены.
  4. Детерминированная приёмка — задача закрывается только по критериям acceptance из карточки; провал фиксируется в Blockers.
  5. Локальность — модели, эмбеддинги, рендер схем и тесты выполняются локально.
  6. Прослеживаемость — решение, схемы, контракты, ревью и коммиты связаны через ID задач.

2. Архитектура

2.1 Компонентная схема

Исходник: diagrams/components-harness.puml.

Слои решения:

Слой Компоненты Назначение
Управление opencode, primary-агент harness, команды /harness-*, глобальная установка явный запуск, маршрутизация ролей, синхронизация артефактов
Роли harness-orchestrator, harness-analyst, harness-architect, harness-coder, harness-qa, harness-doc-writer выполнение работ по зонам ответственности
Модели qwen3.8:27b-64k, tiel-coder:35b-a3b-mtp-128k (text/vision) локальный инференс без внешних API

Артефакты docs/analysis, docs/architecture, docs/qa, docs/guides, src, tests результаты ролей
Инструменты MCP plantuml-render, local-rag, Git проверка/рендер схем, поиск по источникам, версионирование
Пилот FastAPI REST API, NoteService, NoteRepository, SQLite сквозной пример реализации

Поток управления: пользователь вызывает /harness-run T-XXX → команда переключает сессию на primary-агента harness → lead проверяет marker и depends_on → harness-orchestrator ведёт board и приёмку → профильная роль пишет артефакты → orchestrator обновляет board/диаграмму и коммитит.

Общие запреты: правка ~/.config/opencode/**, секреты в коде/логах/коммитах, вложенный вызов sub-agent'ов, выход за пределы диска C:, prod-деплой.

4. Сценарии

S-01. Установка и bootstrap harness

Цель: один раз установить harness глобально и инициализировать его в проекте. Предусловия: репозиторий с исходниками harness доступен, Ollama запущена, модели загружены.

Исходник: diagrams/seq-01-bootstrap.puml.

Результат: агенты, команды, skill, шаблоны и скрипты лежат в ~/.config/opencode/; в проекте созданы harness/process.md, harness/version.json и docs/plan.md. Особенность: default_agent не меняется; после установки агентов обязателен перезапуск opencode. Активация — только явными /harness-*.

S-02. Полный цикл задачи (/harness-run)

Цель: провести задачу от проверки зависимостей до приёмки и коммита. Предусловия: проект инициализирован (harness/process.md), карточка docs/tasks/T-XXX-*.md существует, все depends_on находятся в статусе done.

Исходник: diagrams/seq-02-harness-run.puml.

Результат: задача переведена в done, обновлены board, карточка, activity- диаграмма и SVG, сделан коммит T-XXX: ...; зависимые задачи разблокированы. Ошибки: нет marker — стоп с предложением /harness-init; невыполненные зависимости — стоп без запуска; провал acceptance — failed и причина в Blockers.

S-03. Анализ требований (analyst)

Цель: собрать и уточнить требования, проверить существующие материалы через RAG. Предусловия: есть постановка и доступ к local-rag (при недоступности Ollama RAG работает в режиме FTS5).

Исходник: diagrams/seq-03-analyst.puml.

Результат: docs/analysis/requirements-*.md с атомарными проверяемыми требованиями R-NNN, questions-*.md с открытыми вопросами и допущениями, glossary.md; отчёт orchestrator с рисками и блокерами. Ошибки: недостаток данных оформляется как вопрос, а не как выдуманное требование.

S-04. Архитектура и схемы (architect)

Цель: принять архитектурное решение с альтернативами, оформить схемы и контракты. Предусловия: требования analyst приняты.

Исходник: diagrams/seq-04-architect.puml.

Результат: ADR по шаблону, компонентные/sequence-схемы .puml + .svg, контракты интерфейсов, декомпозиция для coder. Обязательный контроль: каждая схема проходит check_syntax, затем render_file; ошибки синтаксиса устраняются до передачи задачи. Решение без альтернатив недопустимо.

S-05. Реализация и тесты (coder)

Цель: реализовать решение строго по ADR и контрактам. Предусловия: ADR и контракты приняты, задача содержит target локального запуска.

Исходник: diagrams/seq-05-coder.puml.

Результат: код в src/, тесты в tests/, CI/CD-подготовка (Dockerfile, compose, Makefile, скрипты), зелёные тесты и локально поднятый сервис. Ошибки: падение тестов исправляется без ослабления assert'ов; при нехватке контекста — стоп и блокер, а не частичная реализация.

S-06. QA-приёмка (qa)

Цель: независимо проверить артефакты против acceptance. Предусловия: результаты роли переданы orchestrator'ом.

Исходник: diagrams/seq-06-qa.puml.

Результат: docs/qa/review-T-XXX.md с таблицей «критерий → pass/fail», замечаниями по severity и вердиктом accept/reject; независимый прогон тестов (read-only) и визуальная проверка схем. Ошибки: reject возвращает задачу на исправление; QA сам артефакты не правит.

S-07. Документирование (doc-writer)

Цель: привести документацию к фактическому решению. Предусловия: ADR, контракты и реализация доступны.

Исходник: diagrams/seq-07-doc-writer.puml.

Результат: README, runbook, гайды, финализация ADR по шаблону; ссылки относительные, команды проверены. Ограничение: менять смысл ADR и контрактов нельзя — только форму и полноту.

S-08. Синхронизация board (harness-board-update)

Цель: привести план, карточки и activity-диаграмму к фактическому состоянию. Предусловия: проект инициализирован; выполнены задачи или изменились статусы.

Исходник: diagrams/seq-08-harness-board-update.puml.

Результат: harness lead делегирует harness-orchestrator обновление docs/plan.md, карточек, цветов docs/activity.puml, перерендер docs/activity.svg, запись хэшей коммитов и коммит chore: board update (...). Правило: при расхождении истиной считается карточка задачи.

S-09. Отчёт по board (harness-board-report)

Цель: получить сводку без изменения артефактов. Предусловия: проект инициализирован.

Исходник: diagrams/seq-09-harness-board-report.puml.

Результат: harness lead делегирует harness-orchestrator read-only сводку: таблица статусов, список готовых к старту задач, failed/blocked с причинами, %done, проверка «висячих» зависимостей, 1–3 рекомендации. Правило: сценарий строго read-only, ничего не коммитится.

S-10. Ошибки, retry и блокировки

Цель: обработать провал приёмки предсказуемо и не потерять историю. Предусловия: роль вернула результат, orchestrator выполнил приёмку.

Исходник: diagrams/seq-10-errors.puml.

Результат: при провале задача получает failed, причина и вывод пишутся в карточку; выполняется до 3 попыток исправления; после исчерпания — blocked и эскалация пользователю. История ошибок не удаляется при исправлении.

S-11. Пилотный end-to-end цикл T-013

Цель: доказать работоспособность полного цикла на отдельной задаче. Предусловия: harness собран (T-001..T-012), роли доступны.

Исходник: diagrams/seq-11-pilot-e2e.puml.

Результат: аналитик сформировал требования пилота, архитектор — ADR и компонентную схему, QA — ревью с вердиктом accept; T-013 переведена в done, сделан коммит. Пилот подтвердил, что ролевые промпты достаточно детерминированы.

5. Концептуальная модель классов

Исходник: diagrams/class-harness.puml.

Модель концептуальная: она описывает домен harness (board, задачи, роли, артефакты), а не классы конкретного приложения.

Класс Назначение
PlanBoard board docs/plan.md: загрузка задач, смена статуса, запись коммита
TaskCard карточка задачи: id, роль, зависимости, acceptance, артефакты, блокеры, лог
TaskStatus статусы pending, in_progress, done, failed, blocked
Role абстрактная роль: модель, права, зоны записи, выполнение задачи
Orchestrator, Analyst, Architect, Coder, QA, DocWriter конкретные роли harness
ModelProfile локальная модель, режим thinking, назначение
Artifact артефакт роли с путём, типом и производителем
Diagram PlantUML-исходник и SVG-рендер; проверка и рендер
Review отчёт QA: вердикт и список замечаний
Finding замечание с ID, severity и текстом
Commit git-коммит задачи: хэш и сообщение
Command команда opencode: /harness-run, /harness-board-update, /harness-board-report
HarnessLead primary-агент harness: marker, маршрутизация, отчёт; не пишет файлы
LogEntry запись в логе карточки
RoleResult результат роли: статус, файлы, резюме

Ключевые связи: PlanBoard 1 *-- 0..* TaskCard; TaskCard зависит от других карточек (dependsOn), назначена одной роли и имеет один статус; роль produces много артефактов; Diagram и Review наследуют Artifact; HarnessLead выбирается командой, читает board/карточки и вызывает роли; orchestrator обновляет board и создаёт коммиты.

6. Процесс, статусы и управление

6.1 Жизненный цикл задачи

  1. harness lead проверяет marker проекта и depends_on: все — done.
  2. harness-orchestrator переводит задачу в in_progress (plan, карточка, цвет диаграммы).
  3. Роль выполняет задачу строго по acceptance из карточки.
  4. harness-orchestrator принимает результат; при провале — failed.
  5. Статус → done, запись в log, обновление board/activity/SVG и коммит.

6.2 Статусы

Статус Цвет Значение
pending #D3D3D3 не начата
in_progress #FFE082 в работе
done #90EE90 выполнена и принята
failed #FF9090 ошибка, требуется исправление
blocked #FFB347 внешняя блокировка

Допустимые переходы: pending → in_progress → done; in_progress → failed; failed → in_progress (после исправления); * → blocked при внешней блокировке.

6.3 Обязательный порядок обновления артефактов

  1. docs/plan.md — статус, артефакты, хэш коммита.
  2. docs/tasks/T-XXX-*.md — статус, лог, блокеры.
  3. docs/activity.puml — цвет блока задачи.
  4. Перерендер docs/activity.svg через MCP plantuml-render.
  5. git commit с сообщением T-XXX: ....

6.4 Git-дисциплина

  • Репозиторий в корне проекта, ветка по умолчанию — master.
  • Минимум один коммит на задачу; формат T-XXX: краткое описание.
  • Запрещены git push, git tag, правка истории, коммит секретов и .env.
  • В коммит включаются только файлы задачи.

6.5 Диаграмма выполнения плана

Исходник: docs/activity.puml. Зелёный — done, серый — pending, жёлтый — in_progress, красный — failed, оранжевый — blocked.

7. Пилотный кейс «Мини-CRUD сервис» (T-013)

Пилот проверяет цикл analyst → architect → qa на отдельной задаче: REST CRUD для заметок, SQLite, локальный Docker, детерминированные тесты. Один пользователь, без auth и внешних интеграций.

7.1 Требования

ID Требование
R-001 POST /notes с title, body; ответ 201 с id.
R-002 GET /notes — массив заметок, сортировка по created_at убыв.
R-003 GET /notes/{id}; 404 при отсутствии.
R-004 PUT /notes/{id} с title, body; 404 при отсутствии.
R-005 DELETE /notes/{id}; 204 при успехе, 404 при отсутствии.
R-006 Валидация: title 1..200 символов, body до 10000; ошибка 422.
NFR-1 docker compose up поднимает сервис на порту 8080.
NFR-2 SQLite-файл в volume, переживает рестарт контейнера.
NFR-3 Unit + API-тесты, детерминированные, без сети.

Открытые вопросы пилота: пагинация не нужна (Q-001), поиск по тексту вне пилота (Q-002). Риски: рост SQLite-файла (R1), отсутствие auth — только local/staging (R2). Полные требования: docs/analysis/pilot-requirements.md.

7.2 Архитектурное решение (ADR-001)

Стек: Python 3.12 + FastAPI + SQLAlchemy 2.x (SQLite) + Pydantic v2. Структура: тонкий API-слой → сервисный слой → репозиторий. Тесты: pytest + httpx (ASGI transport). Контейнеризация: python:3.12-slim, docker compose с volume для БД.

Альтернатива Почему отклонена
Flask + SQLite ручная валидация, меньше типизации
Node/Express + better-sqlite3 второй стек в локальном окружении
Django + DRF избыточен для одного CRUD

Полный ADR: docs/architecture/pilot-adr.md.

7.3 REST-контракт

Метод Путь Тело Ответ
POST /notes {title, body} 201 {id, title, body, created_at}
GET /notes — 200 [...]
GET /notes/{id} — 200 / 404
PUT /notes/{id} {title, body} 200 / 404
DELETE /notes/{id} — 204 / 404

Ошибки: {"detail": "..."}; валидация — 422 (Pydantic).

8. Эксплуатация

8.1 Глобальная установка и быстрый старт

  1. Из корня репозитория выполнить глобальную установку: powershell -NoProfile -ExecutionPolicy Bypass -File harness/scripts/install.ps1.
  2. Перезапустить opencode; проверить установку командой /harness-doctor.
  3. В проекте выполнить /harness-init; проверить harness/process.md и docs/plan.md.
  4. Заполнить docs/plan.md, создать карточку по harness/templates/task-card.md.
  5. Запустить задачу командой /harness-run T-XXX.
  6. Сводка: /harness-board-report; синхронизация: /harness-board-update all.
  7. Диаграмма: docs/activity.puml, рендер — docs/activity.svg.

default_agent не переключается на harness: активация только явными /harness-*. Глобальная установка выполняется для текущего пользователя (~/.config/opencode).

8.2 Команды

Команда Аргумент Назначение
/harness-init — создать harness в текущем проекте и marker-файлы
/harness-run T-XXX проверка зависимостей, in_progress, вызов роли, приёмка, коммит
/harness-board-update T-XXX или all сверка статусов, коммитов, activity-диаграммы и SVG
/harness-board-report — read-only сводка: статусы, блокеры, готовые к старту, рекомендации
/harness-doctor — проверка глобальной установки и текущего проекта

8.3 Как добавить задачу

  1. Создать карточку по шаблону harness/templates/task-card.md.
  2. Добавить строку в docs/plan.md по шаблону harness/templates/plan-row.md.
  3. Указать роль, depends_on, acceptance, артефакты.
  4. Запустить harness-run T-XXX после выполнения зависимостей.
  5. После задачи обновить board/карточку/диаграмму и закоммитить.

8.4 Ограничения и риски

  • SQLite не предназначен для конкурентной записи — принято для пилота.
  • Нет auth — сервис только для local/staging.
  • Модели локальные: качество и скорость зависят от железа; при недоступности Ollama RAG работает в режиме FTS5.
  • Схемы и документация требуют периодической сверки с кодом.
  • Ролевые промпты детерминированы, но не гарантируют идеальный результат с первого прохода — предусмотрены failed и retry ≤ 3.

8.5 Сборка HTML

HTML-версия генерируется из этого файла и не требует сети:

python docs/description/build_html.py

Скрипт встраивает все SVG как data:-URI, оборачивает диаграммы в zoomable- фигуры и собирает docs/description/index.html. Шаблон страницы и стили/JS модалки — docs/description/template.html. Требуется Python 3.12 и пакет markdown.

8.6 Диагностика

Симптом Причина Действие
роль не видна в opencode агенты добавлены после старта перезапустить opencode
модель недоступна Ollama не запущена / модель не загружена запустить Ollama, ollama pull
RAG отвечает без эмбеддингов Ollama недоступна работа в режиме FTS5, не блокирует задачу
схема не рендерится ошибка PlantUML check_syntax, исправить .puml, повторить render_file
задача не стартует зависимость не done проверить depends_on и статусы карточек
